Perso XXL webpage customization primer

The DOM is the page API your extension has to understand.

A browser shows pixels, but a content script edits a live object tree. Reliable AI customization depends on giving the agent tools that can inspect that tree, ground the right target, apply a constrained change, and verify what actually happened.

What The DOM Is

The Document Object Model is the browser's live representation of an HTML page. HTML text becomes a tree of nodes: document, html, body, elements, text nodes, attributes, and event listeners. JavaScript reads and changes this tree; the browser then recalculates style, layout, paint, and interaction.

Same page, three views

HTML source Initial text sent by server or generated by app code.
DOM tree Live nodes with attributes, text, children, state, and listeners.
CSSOM Stylesheets and inline styles resolve into computed styles.
Layout tree Visible boxes get positions, sizes, stacking, and overflow.
Pixels The final visual result the user sees and clicks.

What An Agent Must Infer

A user says "hide the Mark Ruber video." The browser does not know what that means. The agent must connect the misspelled human phrase to a DOM target, choose the correct ancestor to hide, and avoid changing other video cards that share the same classes. 

const title = document.querySelector(".title");
const card = title.closest(".video-card");
card.style.display = "none";

That code is simple only after the target is known. Most failures in this project are grounding failures: wrong element, too broad selector, hidden target missing from context, or a selector that breaks after rerender.

How Extensions Usually Interact With The DOM

Chrome extension mental model

Web Page

  • Owns app JavaScript and DOM
  • Rerenders with React, Vue, or server updates
  • Can change classes, layout, and text after load
isolated world

Content Script

  • Can read and mutate page DOM
  • Can add CSS and event listeners
  • Cannot directly call page functions unless bridged

Extension pipeline

User intent Prompt, clicked element, or persistent preference.
Observe DOM summary, selected node, accessibility, layout, screenshot crop.
Plan Model returns declarative targets and rules, not arbitrary scripts.
Execute Trusted code applies CSS, hides nodes, inserts assets, or runs approved capability.
Verify Check match count, target correctness, blast radius, persistence, and UI safety.

What Perso XXL Can Do Well

  • Read the live DOM through a content script.
  • Use selected-element context when the user clicks a target.
  • Generate a declarative transform plan with target selectors and typed rules.
  • Apply style and visibility changes through trusted executor code.
  • Reapply a plan after mutations when the page rerenders.
  • Log matched elements so the harness can diagnose selector quality.

What Perso XXL Should Avoid

  • Running arbitrary model-written JavaScript by default.
  • Trusting totalMatched > 0 as proof of success.
  • Using benchmark-only handles like data-uid on real websites.
  • Hiding broad classes such as every .video-card when the user meant one creator.
  • Assuming visible text is enough; ARIA, layout, and nearby family often matter.
  • Changing cross-origin iframes, browser UI, or extension-protected pages without host permissions.

Can And Cannot Do

Capability Status Reliability note
Change colors, spacing, fonts, borders, and backgrounds Good fit Use scoped CSS rules and computed-style verification.
Hide or remove cards, banners, feeds, and panels Good fit Choose the semantic container, then check forbidden siblings still exist.
Insert icons, labels, or helper UI Needs trusted asset tools Use approved icon libraries, accessibility labels, and collision checks.
Filter YouTube-like content by creator, title, or sponsored badge Needs DOM search and repair Robust tools must handle typos, lazy-loaded cards, and rerenders.
Stop scrolling or change page behavior Capability module Provide a named scroll-lock tool instead of free-form script.
Theme a whole page from a broad idea Hard Needs style inventory, asset generation or lookup, visual checks, and rollback.
Edit server data, bypass site security, or access unavailable account content Cannot rely on it A content script changes what the browser displays; it does not own the server.
Read or modify cross-origin iframe contents Usually blocked Browser security boundaries apply unless the extension has matching permissions and frame access.

Tools To Give The Agent

The repo's DOMFS experiment already points in the right direction: expose an outline, find results, local inspections, nearby family, and proposed selectors. The next step is making these real interactive tools inside the Perso XXL extension, with verification after every important action.

dom.outline() Page landmarks, regions, headings, forms, cards, and node counts.
dom.find(query) Semantic and fuzzy search over visible text, ARIA names, ids, test ids, and nearby labels.
dom.inspect(target) Tag, role, text, attributes, parents, siblings, children, proposed selectors, and event hints.
selector.probe(selector) Match count, sample nodes, bounds, styles, visibility, and whether matches are related.
layout.snapshot() Bounding boxes, viewport position, overlap, z-index, overflow, and clickability.
a11y.snapshot() Role/name tree, tab stops, hidden controls, and whether important actions remain accessible.
screenshot.crop(target) Optional visual grounding around selected or candidate nodes for models that can see images.
plan.apply(plan) Only accepts validated declarative operations and returns exact changed-node diagnostics.
plan.verify(goal) Checks target success, forbidden changes, rerender persistence, and layout integrity.
selector.repair(goal) When a selector is empty or too broad, search by text fingerprint, family, and stable attributes.
capability.run(name) Trusted modules for scroll lock, icon insertion, theme application, physics, and focus helpers.
clarify.question() For ambiguous requests, low-confidence lookup, risky broad changes, or missing permissions.

Selector Strategy

  1. Prefer user-selected node when available.
  2. Prefer stable semantic anchors: role, accessible name, visible text, id, data-testid, and meaningful attributes.
  3. Scope selectors to a parent region before using common classes.
  4. Probe every selector before applying the plan.
  5. Reject broad matches unless the task explicitly asks for a broad change.
  6. Store a fallback fingerprint for rerender repair: text, role, parent text, and relative family.

Execution Strategy

  1. Model proposes targetMap plus typed rules.
  2. Validator checks schema, CSS allowlist, selector syntax, and permission scope.
  3. Executor applies changes using deterministic code.
  4. Verifier checks intended targets and forbidden nodes.
  5. Mutation observer reapplies or repairs after SPA rerenders.
  6. Rollback if verification fails or blast radius is too large.

Why The Harness Matters

The current research harness already creates a local web zoo, runs browser tasks, captures screenshots, grades DOM outcomes, and compares normal context against DOMFS context. That is exactly the right environment for improving an extension agent, because it separates real improvement from lucky demos.

Practical target: make every new Perso XXL tool prove itself on tasks like selected card color, hidden warning panel, typo-based creator filtering, sponsored content removal, scroll lock, and broad theme changes. Keep deterministic DOM/style/accessibility graders as the default, then add visual or model judges only when the task genuinely needs them.
